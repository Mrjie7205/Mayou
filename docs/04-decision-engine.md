# 04 · 决策引擎

> 输入完整局面，输出每张可打牌的打分。
> 工作量约 20%，但开源可复用度最高。

## 输出格式

引擎对当前局面，对**自己手牌中每张可打的牌**给出：

```
{
  tile: "5筒",
  attack_score: 0.62,        # 进攻分 0-1
  defense_score: 0.81,       # 防守分 0-1（高=安全）
  combined_score: 0.71,      # 加权综合
  details: {
    shanten_after: 1,        # 打这张后向听数
    win_probability: 0.18,   # 蒙特卡洛胡牌概率
    expected_fan: 2.3,       # 期望番数
    danger_per_seat: {       # 对每家的危险度
      left: 0.05,
      across: 0.32,
      right: 0.12
    }
  }
}
```

UI 展示推荐 `combined_score` 最高的，悬停看 `details`。

## 三个子系统

### 4.1 向听数（shanten）

**方案**：**从零自写**（见 [ADR-002](decisions/ADR-002-game-switch.md)）。

为什么不 fork 现成麻将库：株洲碰胡的胡牌型是「全刻子 + 1 对将」，没有顺子。几乎所有开源麻将库（python-mahjong / mahjong / 日麻库）都假设有顺子分支，fork 过来要砍掉的代码比新写还多。而且株洲碰胡刻子型 shanten 算法本身极简单，暴力枚举几十行 Python 就够。

要做的：

- **刻子型 shanten 计算**
  - 三色（筒索万）齐全，序数牌 1-9 各 4 张（⚠️ 单色变体确认见 docs/07 §1）
  - **无字牌、无赖子**：标准序数枚举
  - **无吃牌**：副露区数据结构只有碰/杠
  - **无顺子胡型**：搜索时不考虑顺子分支，只数刻子 + 对子 + 将
  - 乱将：任意对子可做将
  - 支持特殊胡牌型加番判定：清一色（三色版本下）、全求人、四暗刻、（⚠️ 七对子待平台确认）

- **听牌枚举**：返回所有听牌组合（单刻 / 双碰 / 单钓将 / 全求人单钓）

预计代码量 300-500 行，比 fork 改造路径更短。

详细规则见 [07-zhuzhou-pengHu-rules.md](07-zhuzhou-pengHu-rules.md)。

### 4.2 进攻评分：蒙特卡洛

**思路**：对每张可打牌，假装打出去，模拟剩余局面 N 次，统计胡牌结果。

```
对每张可打牌 t:
    模拟 1000 次:
        基于状态机的剩余牌山随机发牌
        模拟自己摸打 X 步（X=平均还有几手）
        其他家用简化策略（随机打或最大向听数下降）
        记录是否胡、胡的番数
    win_prob[t] = 胡的次数 / 1000
    expected_fan[t] = 胡时的平均番数
    attack_score[t] = f(win_prob, expected_fan, shanten_after)
```

**性能取舍**：1000 次模拟是起点。如果性能预算（80ms）跑不完，降到 500 或 200。模拟次数低噪声大，但比不算强。

**对手简化策略**：MVP-2 阶段对手用"最大向听数下降"启发式即可，不递归调用引擎（会无限循环）。

### 4.3 防守评分

完全用规则，不需要训模型。

#### 现物

某家自己打过的牌，再打一遍 100% 安全（那家不可能胡自己打过的牌）。

```
for tile in 自己可打牌:
    for seat in [left, across, right]:
        if tile in 该家弃牌区:
            danger[seat][tile] = 0
```

#### ~~筋~~（株洲碰胡不适用）

「筋」依赖两面听（顺子搭子），而株洲碰胡胡牌型禁止顺子。**整个筋概念在本玩法里不成立**，不要照抄日麻防守逻辑。

#### ~~壁~~（株洲碰胡大部分不适用）

壁的主要作用是阻碍顺子搭子。株洲碰胡只有刻子胡型，壁在阻碍「暗刻形成」上有微弱意义（如某张牌 3 张已可见，对手剩下手里最多还有 1 张，无法形成暗刻），但信号强度远低于现物。

Sprint 7 实做时按这个微弱信号决定是否引入。

#### 对手单骑/双碰预测（株洲碰胡的主防守信号）

代替筋/壁，株洲碰胡的核心防守信号是预测对手听的是什么对子：

- 某家碰过 X 后，听张大概率是「X 同色相邻 / 已碰张配对升级」型——具体启发式 Sprint 7 设计
- 某家弃牌很少 → 手里很多对子，可能听双碰
- 某家弃牌全是序数边缘（1、9） → 手里集中在中段，听张大概率在中段

#### 综合

```
defense_score[t] = min(对每家的安全度)
对每家的安全度 = 1 - 危险度
危险度 = w1 * 是否现物的反指标
       + w2 * 单骑/双碰预测的命中度
       + w3 * 该家是否疑似听牌
       + w4 * (可选) 壁信号
```

权重初始全部均匀，实战调。

### 4.4 综合融合

```
combined_score = attack_score * α + defense_score * β
```

α、β 动态：

- 自己已听 → α 大幅高，β 降低
- 自己分高、对手疑似听牌 → β 升高
- 对手都还远（向听数高）→ α 升高
- 最后几张时 → α 降低（搏胡 vs 防守反而要慎重）

初始权重和场景规则在 `src/engine/weights.py`，**版本化**，每次调参 commit 一次。

## 不做的事

- **不接 Mortal、NAGA 等日麻 AI**：规则不通，强行接 = 自己造一个不准的引擎
- **不训自己的神经网络**：成本不在预算内
- **不做对手手牌精确预测**：只做"疑似听牌"二分判定
- **不做"应该碰吗""应该杠吗"建议**（MVP-2 阶段）：碰杠由 Max 决定，引擎只在自己出牌时算

## 性能预算

每次推荐计算 ≤80ms。组成：

| 步骤 | 预算 |
|---|---|
| shanten 算各张 | 10ms |
| 蒙特卡洛 1000 次 | 50ms |
| 防守评分 | 5ms |
| 融合 + 排序 | 5ms |
| 余量 | 10ms |

蒙特卡洛是大头。性能不够时第一个调整。

## 可视化（强制）

UI 调试面板必须能查看：

- 每张可打牌的 attack/defense/combined 分项
- 蒙特卡洛模拟次数和当前耗时
- 当前权重 α、β
- 局势识别结果（"自己听牌"/"对手疑似听牌"等标志位）

引擎不是黑盒，所有打分都能追溯。

## 阶段性目标

- **Sprint 5**：shanten 正确，能识别听牌
- **Sprint 6**：进攻分能算，对比"什么都不算就打最右边"明显更优
- **Sprint 7**：防守分接入，能避开明显危险牌
- **Sprint 8**：在欢乐场实战，Max 主观觉得"差不多算个一般人"
