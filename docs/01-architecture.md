# 01 · 架构总览

> 给"我想理解 Mayou 怎么跑"的人看。
> 不读代码就能看懂。

## 一句话架构

**截图 → 认牌 → 记账 → 算分 → 显示**，五步循环，每 200ms 跑一次。

## 五层

```
┌────────────────────────────────────────┐
│  云游戏窗口（不归我们管）              │
└────────────────────────────────────────┘
              │ 截屏
              ▼
┌────────────────────────────────────────┐
│  ① 采集层 (src/capture/)               │
│  - 定位窗口、按配置裁剪关心区域        │
│  - 每 200ms 一帧                       │
└────────────────────────────────────────┘
              │ 图像帧
              ▼
┌────────────────────────────────────────┐
│  ② 识别层 (src/recognize/)             │
│  - 模板匹配，把图块翻译成"5万"         │
│  - 帧间差分，只关注变化                │
└────────────────────────────────────────┘
              │ 结构化牌符（带位置）
              ▼
┌────────────────────────────────────────┐
│  ③ 状态机 (src/state/)                 │
│  - 维护"账本"：4家手牌/弃牌/碰杠      │
│  - 把识别变化翻译成游戏事件            │
└────────────────────────────────────────┘
              │ 完整局面状态
              ▼
┌────────────────────────────────────────┐
│  ④ 引擎层 (src/engine/)                │
│  - shanten + 蒙特卡洛 + 防守评分       │
│  - 每张可打牌打分                      │
└────────────────────────────────────────┘
              │ 推荐 + 分项数据
              ▼
┌────────────────────────────────────────┐
│  ⑤ UI 层 (src/ui/)                     │
│  - 悬浮窗显示建议、剩余牌、危险提示   │
│  - 调试模式：每层中间结果可视化        │
└────────────────────────────────────────┘
```

## 各层职责（明确边界，避免乱写）

### ① 采集层
- **做**：截图、按 `assets/configs/<platform>.json` 配置裁剪区域
- **不做**：识别任何内容（哪怕只是"判断这块是不是空白"）
- **输出**：图像帧 + 时间戳

### ② 识别层
- **做**：把图像块翻译成"5万""5筒""碰杠组"
- **不做**：理解牌局状态（"谁打了""轮到谁"完全不管）
- **输出**：结构化牌符列表 + 位置信息

### ③ 状态机
- **做**：账本维护，事件检测
- **不做**：任何决策评估
- **输出**：完整局面快照 + 事件流

### ④ 引擎层
- **做**：纯计算，输入局面输出建议
- **不做**：任何 IO、任何屏幕相关、任何 UI 相关
- **输出**：每张可打牌的分项打分 + 推荐

### ⑤ UI 层
- **做**：展示、用户交互、调试可视化
- **不做**：任何识别或决策逻辑
- **输入**：状态机快照 + 引擎打分

## 数据流为什么是单向的

故意设计成 ①→②→③→④→⑤ 单向。原因：

- **可测试**：每层都能用假数据单独测
- **可调试**：出问题往上游层找，不绕圈
- **可替换**：未来想换识别方案（比如换平台），只动 ②，其他层零改动

唯一例外：UI 层（⑤）有"用户手动修正"按钮，可以回写到状态机（③）。比如识别错了，Max 点一下"对家其实碰的是 3 条"，状态机更新。**只有 UI → 状态机这一条反向通道，其他反向通道一律禁止**。

## 性能预算

每帧 200ms 内完成 ①→⑤ 全流程。预算分配：

| 层 | 预算 |
|---|---|
| 截图 | ≤10ms |
| 识别 | ≤80ms |
| 状态机 | ≤20ms |
| 引擎 | ≤80ms（建议只在轮到自己时计算） |
| UI 渲染 | ≤10ms |

引擎是大头。蒙特卡洛模拟次数要调到这个预算内，必要时降模拟次数换实时性。

## 单进程，不分布式

整个程序一个 Python 进程跑。

为什么不拆成"采集进程 + 识别进程 + 引擎进程"：

- 单平台单 UI，吞吐量需求小
- 多进程通信成本高于直接调用
- 调试更难
- Max 不需要扩展性，需要简单

## 配置驱动

平台相关的东西全部进 `assets/configs/<platform>.json`：

- 窗口标题模式
- 各区域裁剪坐标
- 牌面预期尺寸范围
- 颜色容差

换平台 = 改配置 + 重新采模板，**不动代码**（理论上）。

## 与 trading-terminal 的关系

无直接关系。但**工程习惯继承**：

- 前端优先
- Max 不手动改文件
- 配置版本化
- 每层可独立可视化
